# 用户会话归档设计

**日期：** 2026-08-31  
**状态：** 待用户审阅  
**范围：** `arc-knowledge-web` 与 `arc-knowledge-ai`

## 1. 背景

当前侧边栏按“知识空间 → 会话”展示当前用户的全部会话。会话数量增长后，已经结束或暂时不重要的会话会持续占用日常工作区，削弱当前任务的可见性。

现有会话已经由 `tenant_id`、`user_id` 和不可变的 `space_id` 共同约束，适合增加用户级生命周期状态。归档不是删除：它只改变会话是否出现在日常工作区，不删除消息、附件、引用或记忆。

## 2. 目标

- 用户可以从活跃会话列表归档自己的会话。
- 归档会话立即退出日常侧边栏。
- 用户可以在个人设置的“已归档聊天”中按知识空间查找、搜索和恢复会话。
- 恢复后的会话回到原知识空间。
- 归档与恢复具有明确的所有权校验、并发语义、错误反馈和自动化测试。
- 当前管理配置与新增个人设置保持清晰分离。

## 3. 非目标

- 本阶段不实现共享会话或多人分别归档同一会话。
- 本阶段不改变会话所属知识空间。
- 本阶段不删除消息、附件、引用、记忆或文档。
- 本阶段不在归档时自动清理历史数据。
- 本阶段不实现批量归档、自动归档或归档保留期限。
- 置顶交互与接口留给后续阶段；本设计只为其保留兼容的数据字段与排序语义。

## 4. 产品模型

### 4.1 生命周期

会话具有以下用户可见状态：

| 状态 | 判定 | 日常侧边栏 | 个人设置 |
|---|---|---|---|
| 活跃 | `archived_at IS NULL` | 显示在所属空间下 | 不显示 |
| 置顶 | 活跃且 `pinned_at IS NOT NULL` | 显示在所属空间顶部 | 不显示 |
| 已归档 | `archived_at IS NOT NULL` | 不显示 | 显示在“已归档聊天” |

归档会话时必须清空 `pinned_at`。恢复会话不会恢复旧的置顶状态。

### 4.2 会话行操作

- 桌面端会话行在 hover 或键盘聚焦时显示“置顶”和“归档”操作。
- 触摸设备通过会话行的“更多”菜单访问相同操作。
- 本阶段只实现“归档”；置顶按钮可在置顶阶段一并上线，不能交付无行为的占位按钮。
- 活跃会话列表不再把物理删除作为日常主操作。
- 归档可撤销，因此不弹确认框。
- 归档成功后显示短暂提示“已归档 · 撤销”；撤销实际调用恢复接口。

### 4.3 当前会话被归档

如果用户归档当前打开的会话：

1. 服务端归档成功后，前端才从活跃列表移除会话。
2. 清除该会话的未读通知。
3. 停止把该会话作为当前查看对象。
4. 聊天页进入“新会话”空状态，不自动打开另一条历史会话。
5. 保留消息、附件、引用和本地草稿；恢复后可以继续查看。

### 4.4 运行中的会话

处于 `waiting_files` 或 `answering` 的会话不能归档。前端应禁用归档操作并解释原因，后端必须再次校验并在竞态发生时返回 `409 SESSION_BUSY`。

`completed`、`answer_failed` 和 `cancelled` 状态允许归档。用户可以先取消无法继续的轮次，再归档会话。

### 4.5 个人设置入口

- 顶部头像菜单新增“个人设置”。
- 新增用户设置路由与布局，归档页面路由为 `/settings/archived-chats`。
- 侧边栏底部现有 `/admin` 入口改名为“管理配置”，避免与用户设置混淆。
- 个人设置与管理配置采用独立路由和权限边界。

### 4.6 已归档聊天页面

- 页面默认展示当前用户在当前租户下的全部归档会话。
- 会话按知识空间分组；空间组可折叠。
- 组内按 `archived_at DESC` 排序。
- 每个空间组显示空间名、会话数量和空间状态。
- 每行显示会话标题、归档时间和恢复操作。
- 页面支持按会话标题搜索和按空间筛选。
- “没有归档会话”与“搜索无结果”使用不同空状态。
- 查询采用服务端分页，不要求一次加载全部历史。

### 4.7 恢复语义

- 原空间为 `active` 时，会话恢复到原空间。
- 原空间为 `archived` 时，页面显示“空间已归档”，恢复操作改为“先恢复空间”。有空间管理权限的用户可以先调用空间恢复操作；没有权限的用户看到“联系管理员恢复空间”。
- 系统不能静默把会话迁移到其他空间。
- 空间在恢复请求期间被归档时，后端返回 `409 SPACE_ARCHIVED`，前端刷新该空间状态。
- 恢复成功后，从归档列表移除该会话并提示“已恢复到「空间名」”。

当前空间删除已经使用 `status = 'archived'`，但项目尚无正式恢复接口。完整交付依赖新增幂等的 `POST /spaces/{space_id}/restore`。该接口沿用空间管理权限，不能因为用户拥有空间中的某条会话就自动获得恢复共享空间的权限。

## 5. 数据设计

### 5.1 表结构

为 `sessions` 增加两个 nullable 字段：

```sql
ALTER TABLE sessions
    ADD COLUMN IF NOT EXISTS archived_at TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS pinned_at TIMESTAMPTZ;
```

使用时间戳而不是布尔值，因为归档中心需要按归档时间排序，后续置顶也需要稳定排序。

新增部分索引：

```sql
CREATE INDEX IF NOT EXISTS idx_sessions_active_space
    ON sessions (tenant_id, user_id, space_id, updated_at DESC)
    WHERE archived_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_sessions_archived_user
    ON sessions (tenant_id, user_id, archived_at DESC)
    WHERE archived_at IS NOT NULL;
```

旧会话的两个字段均为 `NULL`，迁移后仍保持活跃，不需要回填。

### 5.2 领域模型

`Session` 增加：

```text
archived_at: datetime | None
pinned_at: datetime | None
```

归档是会话自身的用户状态。当前会话属于单一用户，因此不引入独立 `user_session_states` 表。若未来会话支持共享且不同用户需要不同归档状态，再迁移到关联表。

## 6. API 设计

### 6.1 归档

```http
POST /sessions/{session_id}/archive
```

- 只允许当前 `tenant_id + user_id` 拥有的会话。
- 已归档会话重复归档视为成功。
- 成功返回 `204 No Content`。
- 会话不存在或不属于当前用户返回 `404`。
- 会话仍在运行返回 `409`，错误码为 `SESSION_BUSY`。
- 原子更新 `archived_at = NOW(), pinned_at = NULL`。

### 6.2 恢复

```http
POST /sessions/{session_id}/restore
```

- 已恢复会话重复恢复视为成功。
- 成功返回 `204 No Content`。
- 会话不存在或不属于当前用户返回 `404`。
- 原空间已归档返回 `409`，错误码为 `SPACE_ARCHIVED`。
- 原子更新 `archived_at = NULL`。

### 6.3 归档列表

```http
GET /sessions/archived?query=&space_id=&limit=50&offset=0
```

响应保持扁平，由前端按空间分组：

```json
{
  "items": [
    {
      "session_id": "uuid",
      "title": "旧版上传流程",
      "message_count": 12,
      "archived_at": "2026-08-21T09:30:00Z",
      "space": {
        "space_id": "uuid",
        "name": "产品文档",
        "status": "active"
      }
    }
  ],
  "total": 1
}
```

搜索只匹配当前用户归档会话的标题。`space_id` 只作为当前用户归档结果的筛选条件。

静态路由 `/sessions/archived` 必须在动态路由 `/sessions/{session_id}` 之前注册，避免 `archived` 被当作会话 ID。`total` 来自独立计数查询，不能使用当前分页结果长度代替。

### 6.4 现有接口变化

- `GET /sessions` 固定增加 `archived_at IS NULL`，继续按空间返回活跃会话。
- `SessionOut` 增加 `archived_at` 和 `pinned_at`，使客户端能够识别服务端权威状态。
- 现有 `DELETE /sessions/{id}` 暂时保留供未来的数据清理或管理流程使用，但从日常会话 UI 移除。

### 6.5 空间恢复依赖

```http
POST /spaces/{space_id}/restore
```

- 重复恢复视为成功，返回 `204 No Content`。
- 不存在、跨租户或无权限统一返回 `404`，避免泄露空间存在性。
- 恢复空间不会自动恢复其中的会话；用户仍需明确恢复目标会话。
- 当前 MVP 尚未建立细粒度 RBAC 时，该接口沿用现有空间创建和归档的授权边界，不能在会话归档功能中另造一套权限规则。

## 7. 后端职责

### 7.1 Repository

`SessionRepository` 增加：

- `archive(session_id, tenant_id, user_id)`
- `restore(session_id, tenant_id, user_id)`
- `list_archived(tenant_id, user_id, query, space_id, limit, offset)`
- 活跃 `list()` 默认过滤 `archived_at IS NULL`

归档列表查询连接 `spaces`，返回空间名称和状态。所有查询必须同时使用租户和用户过滤，跨用户操作统一表现为未找到。

### 7.2 Service

`SessionService` 负责：

- 归档前检查未完成轮次。
- 恢复前检查原空间状态。
- 把 Repository 的状态转换成稳定的业务错误。
- 保证归档和恢复幂等。

忙碌状态的判断必须来自数据库中的权威轮次状态，不能依赖前端本地运行时。

### 7.3 Router

Router 只负责参数验证、用户上下文、响应模型和业务错误到 HTTP 状态的映射，不直接拼接归档 SQL。

## 8. 前端职责

### 8.1 组件边界

- `SessionRow.vue`：会话标题、未读状态、置顶/归档入口和可访问性。
- `UserSettingsLayout.vue`：用户设置的二级导航和内容区。
- `ArchivedChatsView.vue`：查询、搜索、空间筛选、分组、空状态和恢复。
- `AppSidebar.vue`：组合导航、空间与会话组件，不继续承载归档业务细节。
- `AppHeader.vue`：头像菜单增加“个人设置”。

### 8.2 Store 边界

- `chatStore.archiveSession(id)` 处理活跃列表、当前会话、通知和后台运行时。
- 新建 `archiveStore`，只负责归档列表查询、分组、筛选和恢复。
- `archiveStore` 不持有消息正文或聊天流运行时。
- 恢复后不主动切换当前空间；用户回到该空间时，正常会话列表重新加载即可看到恢复结果。

### 8.3 状态更新顺序

归档采用服务端确认后更新：

1. 行操作进入 loading，阻止重复提交。
2. 调用归档接口。
3. 成功后从活跃列表移除并处理当前会话。
4. 显示可撤销提示。
5. 失败时保留原列表，不需要回滚乐观更新。

恢复采用相同原则：服务端成功后才从归档列表移除。

## 9. 错误处理

| 场景 | 服务端 | 前端 |
|---|---|---|
| 会话仍在处理 | `409 SESSION_BUSY` | 提示完成或取消后再归档 |
| 会话不存在或越权 | `404` | 刷新当前列表，显示通用未找到提示 |
| 原空间已归档 | `409 SPACE_ARCHIVED` | 标记空间已归档，显示“先恢复空间” |
| 用户无空间恢复权限 | `404` | 显示“联系管理员恢复空间” |
| 归档列表加载失败 | 传播标准错误 | 保留页面结构并提供重试 |
| 重复归档或恢复 | `204` | 按成功处理并同步本地状态 |
| 网络失败 | 不改变数据 | 保留原行，允许重试 |

## 10. 可访问性

- 归档和恢复使用真实 `button`。
- 图标按钮提供具体的 `aria-label`，例如“归档会话 接入鉴权方案”。
- hover 出现的操作也必须在 `focus-within` 时可见。
- 触摸设备不依赖 hover。
- 空间分组折叠按钮暴露 `aria-expanded`。
- 搜索框有可见标签或等价的可访问名称。
- loading、成功和失败状态不得只靠颜色表达。

## 11. 测试策略

### 11.1 后端单元测试

- 旧会话迁移后默认活跃。
- 活跃列表排除归档会话。
- 归档列表只返回当前租户和当前用户的数据。
- 标题搜索和空间筛选不能绕过所有权过滤。
- 归档与恢复幂等。
- 归档清空 `pinned_at`。
- 运行中的会话返回 `SESSION_BUSY`。
- 已归档空间阻止恢复。
- 跨用户归档和恢复返回 `404`。
- 归档列表正确返回空间名称与状态。

### 11.2 前端组件与 Store 测试

- 会话行归档按钮支持鼠标和键盘。
- 归档成功后从当前空间移除。
- 归档当前会话后进入新会话状态。
- 未读通知在归档后清除。
- 归档失败时会话保留原位。
- 撤销调用恢复接口。
- 归档中心按空间分组并按归档时间排序。
- 搜索、空间筛选和两类空状态正确。
- 空间已归档时禁用直接恢复。
- 恢复失败时归档行保持原位。

### 11.3 端到端测试

核心路径：

1. 用户登录并进入一个空间。
2. 归档一条已完成会话。
3. 会话从侧边栏消失。
4. 从头像菜单进入个人设置。
5. 在对应空间分组中找到该会话。
6. 恢复会话。
7. 返回原空间后，会话重新出现。

另需覆盖运行中会话不可归档、原空间已归档不可恢复，以及用户之间不可见三条安全路径。

## 12. 日志与审计

记录结构化业务事件：

- `session.archived`：`tenant_id`、`user_id`、`session_id`、`space_id`、`archived_at`
- `session.restored`：`tenant_id`、`user_id`、`session_id`、`space_id`、`restored_at`

日志不能包含消息正文、附件内容或提示词。

## 13. 发布与回滚

1. 先发布 nullable 字段和索引迁移。
2. 发布后端过滤、归档、恢复和列表接口。
3. 发布前端个人设置、归档中心和会话行操作。
4. 通过端到端测试后，从日常 UI 移除物理删除入口。

旧前端连接新后端时，`GET /sessions` 仍返回全部未归档会话，行为兼容。新前端连接旧后端时归档接口不可用，因此前后端必须按上述顺序发布。

回滚前端不会丢失数据；回滚后端代码时保留 nullable 字段即可，不需要破坏性数据库回滚。
